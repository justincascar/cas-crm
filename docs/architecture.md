# Architecture

## Why this stack

Justin needs a maintainable system on a Windows PC, without buying hosting yet. The machine had Git but not Node or Python. Node.js 24 LTS was installed with winget so the CRM can run locally in a browser.

- **Next.js** — one codebase for screens and server logic.
- **SQLite via Node’s built-in `node:sqlite`** — persistent file database, no separate database server, no Visual Studio build tools.
- **Database location** — `%LOCALAPPDATA%\CAS-CRM\cas-crm.sqlite` so OneDrive cannot lock it.
- **Stored files** — `%LOCALAPPDATA%\CAS-CRM\files`. Each file is a `documents` row (type tag such as V5C, original filename, link to a vehicle and/or a claim).
- **Tailwind CSS** — layout without a separate design kit.

PostgreSQL can replace SQLite later if CAS hosts a shared office server. Lookup, email and WhatsApp sit behind adapter interfaces so providers can change.

## Date and money rules

- Store timestamps as ISO-8601 UTC text.
- Display in Europe/London, including BST. Calendar “today” and “now” for validation and alerts use `Europe/London` (`londonTodayIso` / `londonNow`), not the server’s default timezone.
- Accident dates cannot be after today’s London date.
- Store money as integer pence. Display with `en-GB` currency formatting.
- Never add claimed + agreed, or treat offered as received.

## Key modules

- `src/lib/domain/rules.ts` — hire, reservation, chaser and agreement rules (tested). Engineer and hire-pack payment chases share the same stop/reset pattern.
- `src/lib/documents/` — CAS letter/email wording (`cas-wording.ts`), Hire Pack terms (`cas-hire-terms.ts`, not invented).
- Payment-request attachments (`src/lib/email/payment-request-pack.ts`). There is no email template titled payment request. The pack is pre-ticked on the prepared repair-invoice or total-loss settlement chase (`repair_payment_chase`, `settlement_payment_chase`). The older keys `payment_chase_1` and `payment_chase_2` still select the same pack if an old draft is opened, but they are no longer offered in the free-standing composer. The ticks are not a send. The handler can untick or add documents, then clicks Send. A missing item is named, for example “Signed hire agreement — not on file”, and is not replaced with another document. The payment request letter is the stored hire pack cover letter (`hire_pack_cover`), current version only. Compose does not generate that letter. The signed hire agreement is the current signed version only; older versions stay in the manual list, unticked. Where a type has more than one version, only the current one is pre-ticked. CAS’s own insurance certificate had no company-level home. It is one company file on Settings: a `documents` row with no claim, type `cas_insurance_certificate`. Until that file is stored, Settings and this email say “CAS's own insurance certificate — not set up”. No certificate is invented. An auto-selected set over 35 MB uses the existing `attachmentsExceedMailboxLimit` refusal (`MAILBOX_ATTACHMENT_LIMIT_BYTES`) and does not send. A claim with none of the pack stored can still be sent as text if nothing is ticked. The documents-page reminder (signed hire agreement and engineer's report) is unchanged.
- Tracked payment chase (`src/lib/domain/payment-chase.ts`, `src/lib/db/payment-ledger.ts`). Repair invoice and total-loss settlement each have their own chase on the same clock as engineer, liability and repair-authorisation chases (`repair_payment`, `settlement_payment` in `src/lib/domain/chase.ts`). Storage is shown beside the repair figure and is not added into it. There is no storage-payment chase. The first email is prepared as soon as an agreed balance is outstanding. Staff click Send. After that send is recorded, the existing three-day reminder interval (a demonstration setting, with the same per-claim override) prepares the next chase. It does not send itself. One automation row means an outage produces at most one catch-up reminder. A part-payment is added to the single `received_pence` total on that head, the chase pauses for review, and the next email uses the reduced balance. A part-payment is never paid. A correction ticked within two minutes replaces the last figure so it is not added twice. A later payment that is not marked as a correction still adds. Full payment stops that chase and records a hire-and-storage review flag. Hire end is not set. On a total loss the existing suggestion (seven London days after a handler-confirmed full payment) can still appear, and staff confirm it separately. Storage end stays an explicit date. A substantive reply pauses for review. An acknowledgement does not resolve the chase. Uncertain wording is flagged and not guessed. A payment with no claim or head of loss is flagged and not allocated. The amount received stays one editable total on `financial_lines`. History events `payment_chase_1_sent` and `payment_chase_2_sent` are still written and are not deleted. CAS’s default insurer payment term is Due on receipt. A prepared invoice or payment request says “Payment is due immediately upon receipt of this invoice.” It is never shown as 0 days. A term stored for one insurer (`known_insurers.payment_term`) is printed as that insurer’s own words and replaces the default. The three-day reminder interval is not that term.
- Hire and repair chronology (`src/lib/domain/justification-chronology.ts`), shown on the claim overview. It filters existing `claim_events` into date order: accident, recovery completed, engineer instructed, engineer inspection booked, engineer inspection attended, both initial insurer letters, the engineer's report received, the engineer's report sent to the insurer, chasers marked as sent, repair authorisation received, the vehicle received for repair, parts ordered, parts delayed when that was recorded, hire ended, storage ended, repairs started and repairs complete. A required step that applies on an open repairable file but is not on the file is stated afterwards, without a date. Parts delayed is optional and is not shown as missing. A total loss does not gain blank workshop lines. A workshop step already recorded stays if the file later becomes a total loss. A file with no engineer instructed and no repair event does not show them either. A stored note of `Recorded from generated` is shown as generated only. A stored send note is shown as sent. A simulated send is not a send. A gap is measured in real days between consecutive repair-progress steps sorted by the date on the row (the next day is 1; 01/09 to 08/09 is 7). Chasers and letters stay on the list and do not reset the gap. A gap of 7 days or more is flagged until that pair is explained. On an open repairable file, nothing recorded for 7 days since the last step is flagged as well, and that flag returns if another 7 days pass after the explanation with no new step. A total loss stops expecting workshop steps. The 7 days is the confirmed review prompt in Settings (`repair_progress_gap_days`), not a legal limit. On a repairable file the storage end is proposed as the earlier of repairs started and repair authorisation, and it is stored only when a handler confirms it. A confirmed end is not rewritten. If that confirmed end is later than repairs started, the file says “Storage end is after repairs started, review”. Explanations are rows in `repair_gap_explanations`. It does not write the steps themselves. Typed loss-of-use dates are not read.
- Head of loss screens (`src/lib/domain/head-screen.ts`, `src/lib/db/head-screen.ts`). Recovery and storage, hire, and vehicle damage each have one screen from the file. Those screens are the record of claimed, offered, agreed and received. Assessed damage’s valuation boxes and Financial summary are working notes in `claim_screen_data` and do not update those figures. The hidden loss-of-use screen stores its dates there too and does not write the file chronology. Recovery and storage are shown together and calculated separately. Vehicle damage shows repairs or total loss, whichever the file is now. On that screen, insurer offers are dated rows in `insurer_offers` (amount, date, optional note, and withdrawn or lapsed). They are not deleted, and they do not set the agreed figure. The agreed figure and the date agreement was reached are saved separately. Hire and recovery do not have that offer list yet. The file and the dashboard keep the short Awaiting decision line and link to that screen. Accept as final on the screen requires confirmation of the write-off before it is saved, and still does not close hire or storage.
- Review payment (`src/lib/domain/payment-review.ts`, `src/lib/db/payment-review.ts`). Logging a payment records the amount on that head and does not open Accept as final or Dispute. When the amount does not cover the head, the chase pauses as before and the file and the dashboard show one Awaiting decision item for that head until staff open it. Opening that item shows the figures then on the file, and the existing Accept as final and Dispute actions, one under the other. A further payment before that choice updates the same item. A payment logged after Accept as final has already settled that head is flagged for review on the file and the dashboard, and the agreed and received figures are not changed. After Dispute, a later payment reduces the outstanding balance and does not open another decision; the chase is already going for the remainder. Recovery, storage, hire, repairs and total loss each have one item. The item shows the amount received, the amount still outstanding, and the insurer's stated reason, or "no reason given". With an agreed figure, the outstanding amount is against that figure. With no agreed figure, it is claimed minus received. On a total loss the comparison is the agreed pre-accident value minus salvage proceeds already recorded: sale proceeds when a sale figure is on the file, otherwise the engineer's salvage value (the existing pre-accident value minus salvage subtraction), and nothing when the insurer is taking the salvage. Those two salvage figures are not added together. Recording or correcting salvage after the payment recalculates the outstanding amount. Accept as final is the permission `acceptPaymentSettlement` on `staff_permissions`, granted to `staff-justin` by the seed and the migration, not by the administrator role and not by username. It sets the agreed figure to the amount received, writes off the shortfall with the reason, and stops that head's chase. It does not close hire or storage, and it does not run unless someone with the permission does it. A direct call without the permission is refused. Dispute / keep chasing needs no permission: the agreed figure stays, the chase resumes for the balance, and the grounds are staff's own words. A later payment that meets the figure stops the chase and flags hire and storage for review without closing them. A head with no claim or invoice is flagged for manual reconciliation and no financial line is created. Two payments before a decision stay one item, using the existing two-minute correction so a ticked correction is not added twice.
- `src/lib/lookups/` — postcode lookup uses free postcodes.io and OpenStreetMap; vehicle lookup remains simulated.
- `src/lib/db/` — schema, seed, queries, claim screen persistence (`claim_screen_data`).
- Optimistic concurrency (`src/lib/db/record-version.ts`). Each editable screen or settings section has its own version: `claim_screen_data.updated_at` for a claim screen, and a row in `record_versions` for a section that is not one of those screens (storage daily rate, bank details, claim facts, hire pack, fleet, an engineer, a staff login, a money head, a figure choice, a chase interval on one file, a total-loss report, and the date-confirmation choices). The page loads that version. The save sends it back. The server writes only when it still matches, inside one immediate transaction. A missing or different version is refused. The person sees who saved the newer version, the Europe/London date and time, which fields changed, their own unsaved entries, and a link to reload. Nothing is merged. Saving Storage does not block Client details. History, notes, chronology events, new offer rows, corrections, gap explanations and financial-circumstances rows are new entries and are not version-checked. A payment or an agreed figure that repeats the same amount within one minute is recorded once. A chase re-reads the file and writes its own automation fields. If a job writes a field on a screen a person has open, that person's save of the screen is refused and the message names the job (for example Payment chase). A storage-end proposal is stored as a proposal only and does not confirm the end. Bank details keep the existing `manageBankDetails` check and the masked audit. A signed-out save is sent to the sign-in page; the form is not kept across that redirect. A refused save keeps the entries on screen.
- Financial circumstances, the impecuniosity checklist and mitigation statements are dated rows on the claim (`financial_circumstances`, `impecuniosity_accounts`, `impecuniosity_checklist_events`, `impecuniosity_concerns`, `impecuniosity_approvals`, `mitigation_statements`). A change adds a row. It does not update the earlier one. Checklist status is the latest handler-set event, not a count of files. The listed evidence set is every bank account for the relevant period, wage slips or a benefit schedule, household commitments, and other income or support. Impecuniosity evidence files use the existing `documents` table with type `impecuniosity_evidence`. The disclosure letter and an email that asserts impecuniosity are refused unless the checklist is Complete and an administrator has approved relying on it. That approval is not a decision that the charges can be recovered. The background note is `docs/impecuniosity-legal-research.md`. There is no client portal for this section. Those rows are added, not edited, so two people can add entries at the same time. A screen that staff edit in place has its own version (see below).
- Pre-hire checks are separate from that gate. Choosing a car only reserves it, and drafting the pack is allowed before the checks. Producing the hire agreement for signature and completing the handover are refused until every person who will drive has a current licence check. On a non-fault file the bank-statement check is also required: a stored bank statement (`documents.document_type = bank_statements`), a bank account listed on Financial circumstances (`impecuniosity_accounts.kind = bank_account`), or a saved no-bank explanation on the latest financial-circumstances row. A fault courtesy file requires the licence check only and still does not create a credit-hire agreement. The checklist does not need to be Complete, and impecuniosity approval is not required. A missing licence check and missing bank-statement evidence can each be overridden on that claim only, and only by an account with the permission `overridePreHireChecks` in `staff_permissions`. That permission is not the administrator role and not approval to rely on impecuniosity. The seed and the migration grant it to Justin Roberts's staff row (`staff-justin`) and to nobody else. The permission is loaded in `recordPrehireOverride` from `staff_permissions`. It does not test the username. A direct call from an account without the permission is refused. Staff without the permission see the hard refusal and no override form. Each override is a separate action, needs a typed reason, and is stored on the claim in `prehire_overrides` (who, when, which check, and the reason). The row is kept if the evidence is added later. Overriding one check does not override the other. `hireAgreementPrehireBlock` and `generateHireAgreementDocument` do not take a bypass flag and do not read the caller's role. They still refuse a check that is missing and has no stored override on that claim. A bank-statement upload on the Hire tab is the same `documents` row Financial circumstances lists. Each file counts. Wage slips do not. An impecuniosity file that is not stored as a bank statement does not. Licence checks are rows in `licence_checks`: the date, OK to drive or Problem found, categories, penalty points, expiry, an optional check code, notes, and an optional upload labelled from the person’s name and the date. Staff open https://www.gov.uk/check-driving-information themselves. The CRM does not call DVLA. Automated checking is only if CAS later secures bulk DVLA access. The licence number already on the file is not this check. A check older than the Settings window (`licence_check_window_days`, default 21) blocks the agreement and the handover until it is rechecked or overridden. 21 days is the demonstration window until Justin confirms it. It matches a GOV.UK check code and is not, by itself, a ruling that CAS must use 21. Bank statements and licence-check uploads can be opened by office staff only. A direct request for the file by a driver or a mechanic is refused. Drivers are party role `driver`, anyone named on Client driver details, and additional drivers named on the hire pack or Additional drivers. An owner, hirer or client who is not one of those is not included. If nobody is recorded as a driver, the client is included. A stored licence number is not the check. There is no separate preview-for-signing or mark-ready-to-sign step; generating the agreement is the step that files it, and it stays unsigned.
- Fleet availability (`src/lib/domain/fleet-availability.ts`, `src/lib/db/fleet-availability.ts`). One rule for Choose a car, the reserve check, swaps, staff bookings and the dashboard counts: open bookings, cars not returned whatever their planned end, and the fleet status. Disagreements are listed on Fleet records to check and never fixed silently. Hire readiness (`src/lib/db/hire-readiness.ts`) holds the mandatory agreement items, the handover gate (checks, daily rate, signed copy or an authorised override) and the signed-copy filing. The daily rate is stored on the hire at reservation (`rate_taken_on`, `rate_group`). It is the GTA figure for the group charged from the table in force in Settings (`src/lib/db/gta-rates.ts`, table `gta_rate_tables`, one row per effective date with its source) plus the uplift % in Settings. The figures in `src/lib/documents/gta.ts` are only the supplied 2026–27 table that seeds Settings once.
- `src/app/` — screens. Server actions write to SQLite. Each claim file has a right-hand viewing pane of operational screens taken from the current CRM.

## Security posture

Staff must sign in. Passwords are stored hashed in SQLite. Sessions use an HTTP-only cookie. Roles are `administrator` or `staff`. Only an administrator can manage staff logins (`/settings/staff`). Overriding a pre-hire check is not part of that role. It is the permission `overridePreHireChecks` on `staff_permissions`, granted per account. Accepting a short payment as the final figure is a separate permission, `acceptPaymentSettlement`, also on `staff_permissions`. Changing the bank details in Settings is `manageBankDetails`, also on `staff_permissions`, granted only to Justin Roberts’s staff row (`staff-justin`). An administrator does not receive these by being an administrator, and the username is not checked. Approval to rely on impecuniosity is a different gate. Anyone who is signed in can currently see every file — there are no per-claim permissions yet. The database still lives on this PC only.

Driving licence numbers are labelled restricted in the UI; that is not yet a separate access level.

Do not put live client data into this prototype until backups and permission levels are agreed.

Microsoft 365 mail for this app is limited to `claims@cascar.co.uk` (2 October 2026). The app registration `6979ea43-e90c-4dba-a3d0-92d0047d9b6a` has an Exchange Online application access policy, RestrictAccess, scoped to the mail-enabled security group **CAS CRM claims mailbox**. That group exists only because the claims address is a shared mailbox, which cannot be the policy scope by itself. Its only member is `claims@cascar.co.uk`. A send or read failure on another mailbox is the restriction working. Do not remove the policy, and do not add other mailboxes to the group, to widen it. Outbound email goes through `sendOutboundEmail`. It calls Microsoft Graph only when `EMAIL_SEND_MODE` is exactly `live` and the three credentials are set. Any other value, including a missing value, records a simulated send and does not contact Graph. A live send with missing or rejected credentials fails on screen and is not recorded as sent. Settings can check the sign-in token without sending an email.
