# Architecture

## Why this stack

Justin needs a maintainable system on a Windows PC, without buying hosting yet. The machine had Git but not Node or Python. Node.js 24 LTS was installed with winget so the CRM can run locally in a browser.

- **Next.js** — one codebase for screens and server logic.
- **SQLite via Node’s built-in `node:sqlite`** — persistent file database, no separate database server, no Visual Studio build tools.
- **Database location** — `%LOCALAPPDATA%\CAS-CRM\cas-crm.sqlite` so OneDrive cannot lock it.
- **Stored files** — `%LOCALAPPDATA%\CAS-CRM\files`. Each file is a `documents` row (type tag such as V5C, original filename, link to a vehicle and/or a claim).
- **Tailwind CSS** — layout without a separate design kit.

PostgreSQL can replace SQLite later if CAS hosts a shared office server. Lookup, email and WhatsApp sit behind adapter interfaces so providers can change.

## Date and money rules

- Store timestamps as ISO-8601 UTC text.
- Display in Europe/London, including BST. Calendar “today” and “now” for validation and alerts use `Europe/London` (`londonTodayIso` / `londonNow`), not the server’s default timezone.
- Accident dates cannot be after today’s London date.
- Store money as integer pence. Display with `en-GB` currency formatting.
- Never add claimed + agreed, or treat offered as received.

## Key modules

- `src/lib/domain/rules.ts` — hire, reservation, chaser and agreement rules (tested). Engineer and hire-pack payment chases share the same stop/reset pattern.
- `src/lib/documents/` — CAS letter/email wording (`cas-wording.ts`), Hire Pack terms (`cas-hire-terms.ts`, not invented).
- Payment-request attachments (`src/lib/email/payment-request-pack.ts`). There is no email template titled payment request. The pack is pre-ticked on the prepared repair-invoice or total-loss settlement chase (`repair_payment_chase`, `settlement_payment_chase`). The older keys `payment_chase_1` and `payment_chase_2` still select the same pack if an old draft is opened, but they are no longer offered in the free-standing composer. The ticks are not a send. The handler can untick or add documents, then clicks Send. A missing item is named, for example “Signed hire agreement — not on file”, and is not replaced with another document. The payment request letter is the stored hire pack cover letter (`hire_pack_cover`), current version only. Compose does not generate that letter. The signed hire agreement is the current signed version only; older versions stay in the manual list, unticked. Where a type has more than one version, only the current one is pre-ticked. CAS’s own insurance certificate had no company-level home. It is one company file on Settings: a `documents` row with no claim, type `cas_insurance_certificate`. Until that file is stored, Settings and this email say “CAS's own insurance certificate — not set up”. No certificate is invented. An auto-selected set over 35 MB uses the existing `attachmentsExceedMailboxLimit` refusal (`MAILBOX_ATTACHMENT_LIMIT_BYTES`) and does not send. A claim with none of the pack stored can still be sent as text if nothing is ticked. The documents-page reminder (signed hire agreement and engineer's report) is unchanged.
- Tracked payment chase (`src/lib/domain/payment-chase.ts`, `src/lib/db/payment-ledger.ts`). Repair invoice and total-loss settlement each have their own chase on the same clock as engineer, liability and repair-authorisation chases (`repair_payment`, `settlement_payment` in `src/lib/domain/chase.ts`). Storage is shown beside the repair figure and is not added into it. There is no storage-payment chase. The first email is prepared as soon as an agreed balance is outstanding. Staff click Send. After that send is recorded, the existing three-day reminder interval (a demonstration setting, with the same per-claim override) prepares the next chase. It does not send itself. One automation row means an outage produces at most one catch-up reminder. A part-payment is added to the single `received_pence` total on that head, the chase pauses for review, and the next email uses the reduced balance. A part-payment is never paid. A correction ticked within two minutes replaces the last figure so it is not added twice. A later payment that is not marked as a correction still adds. Full payment stops that chase and records a hire-and-storage review flag. Hire end is not set. On a total loss the existing suggestion (seven London days after a handler-confirmed full payment) can still appear, and staff confirm it separately. Storage end stays an explicit date. A substantive reply pauses for review. An acknowledgement does not resolve the chase. Uncertain wording is flagged and not guessed. A payment with no claim or head of loss is flagged and not allocated. The amount received stays one editable total on `financial_lines`. History events `payment_chase_1_sent` and `payment_chase_2_sent` are still written and are not deleted. Settings has an insurer payment-term box with no default. Until Justin confirms the number of days, a prepared email says the term is not set and does not invent a due date. The three-day reminder interval is not that term.
- `src/lib/lookups/` — postcode lookup uses free postcodes.io and OpenStreetMap; vehicle lookup remains simulated.
- `src/lib/db/` — schema, seed, queries, claim screen persistence (`claim_screen_data`).
- Financial circumstances, the impecuniosity checklist and mitigation statements are dated rows on the claim (`financial_circumstances`, `impecuniosity_accounts`, `impecuniosity_checklist_events`, `impecuniosity_concerns`, `impecuniosity_approvals`, `mitigation_statements`). A change adds a row. It does not update the earlier one. Checklist status is the latest handler-set event, not a count of files. The listed evidence set is every bank account for the relevant period, wage slips or a benefit schedule, household commitments, and other income or support. Impecuniosity evidence files use the existing `documents` table with type `impecuniosity_evidence`. The disclosure letter and an email that asserts impecuniosity are refused unless the checklist is Complete and an administrator has approved relying on it. That approval is not a decision that the charges can be recovered. The background note is `docs/impecuniosity-legal-research.md`. There is no client portal for this section. Two simultaneous saves are last-write-wins, the same as the rest of the claim record. The screen says so.
- Pre-hire checks are separate from that gate. Before `generateHireAgreementDocument` allocates an agreement number or inserts the document, it refuses unless every person who will drive the hire vehicle has a staff-entered licence check, and the file has either a bank account listed on Financial circumstances (`impecuniosity_accounts.kind = bank_account`) or a saved no-bank explanation on the latest financial-circumstances row. The checklist does not need to be Complete, and impecuniosity approval is not required. A missing licence check and missing bank-statement evidence can each be overridden on that claim only, and only by an account with the permission `overridePreHireChecks` in `staff_permissions`. That permission is not the administrator role and not approval to rely on impecuniosity. The seed and the migration grant it to Justin Roberts's staff row (`staff-justin`) and to nobody else. The permission is loaded in `recordPrehireOverride` from `staff_permissions`. It does not test the username. A direct call from an account without the permission is refused. Staff without the permission see the hard refusal and no override form. Each override is a separate action, needs a typed reason, and is stored on the claim in `prehire_overrides` (who, when, which check, and the reason). The row is kept if the evidence is added later. Overriding one check does not override the other. `hireAgreementPrehireBlock` and `generateHireAgreementDocument` do not take a bypass flag and do not read the caller's role. They still refuse a check that is missing and has no stored override on that claim. Uploaded impecuniosity files are not labelled as bank statements, so a file on its own does not satisfy the bank half. There is no second upload area; bank statements stay on Financial circumstances. Licence checks are rows in `licence_checks`: the check code, categories, points and endorsements, expiry, the date checked, and who recorded it, typed from the free gov.uk/check-driving-licence lookup. The CRM does not call DVLA. Automated checking is only if CAS later secures bulk DVLA access. A check older than 21 days (the demonstration window, not a DVLA ruling) still counts as recorded. The handover screen shows a stale warning and does not stop. Drivers are party role `driver`, anyone named on Client driver details, and additional drivers named on the hire pack or Additional drivers. An owner, hirer or client who is not one of those is not included. If nobody is recorded as a driver, the client is included. A stored licence number is not the check. There is no separate preview-for-signing or mark-ready-to-sign step; generating the agreement is the step that files it, and it stays unsigned.
- `src/app/` — screens. Server actions write to SQLite. Each claim file has a right-hand viewing pane of operational screens taken from the current CRM.

## Security posture

Staff must sign in. Passwords are stored hashed in SQLite. Sessions use an HTTP-only cookie. Roles are `administrator` or `staff`. Only an administrator can manage staff logins (`/settings/staff`). Overriding a pre-hire check is not part of that role. It is the permission `overridePreHireChecks` on `staff_permissions`, granted per account. An administrator does not receive it by being an administrator. Approval to rely on impecuniosity is a different gate. Anyone who is signed in can currently see every file — there are no per-claim permissions yet. The database still lives on this PC only.

Driving licence numbers are labelled restricted in the UI; that is not yet a separate access level.

Do not put live client data into this prototype until backups and permission levels are agreed.
